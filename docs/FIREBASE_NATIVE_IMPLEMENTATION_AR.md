# خطة تنفيذ Firebase الأصلية لمتجر APEX

## الهدف
تشغيل APEX على Firebase فعلياً (Authentication + Cloud Firestore + Cloud Storage + Cloud Functions)، ثم إبقاء النقل المستقبلي إلى Supabase ممكناً عبر طبقة خدمات مستقلة. لا يتم حذف مشروع Supabase أو بياناته أثناء التطوير.

## ما أُنشئ في المرحلة الأولى
- تهيئة Firebase Web SDK بإصدار مثبت ومحدّد.
- خدمات Auth للتسجيل بالبريد وكلمة المرور، التحقق من البريد، الدخول، الخروج، استعادة كلمة المرور، وتحديث بيانات العميل.
- طبقة بيانات للمنتجات والبنرات ووسائل الدفع والطلبات.
- استدعاء آمن بأسماء محددة للوظائف الست عبر Callable Functions.
- رفع الصور إلى Cloud Storage.
- قواعد Firestore وStorage مغلقة افتراضياً، وصلاحيات المدير تعتمد على Custom Claims موثوقة لا على حقول قابلة للتعديل من العميل.
- فحوص syntax في GitHub Actions.

## متطلبات التهيئة قبل تشغيل التطبيق
1. تأكيد أن مشروع Firebase المقصود هو `apex-3c12f`.
2. تسجيل Web App من Firebase Console ونسخ إعداداته العامة إلى `firebase/runtime-config.js` (يُنشأ محلياً ولا تُضاف أسرار خادم إليه).
3. تفعيل Email/Password في Firebase Authentication وإعداد نطاق GitHub Pages ضمن Authorized domains.
4. إنشاء Firestore وStorage في المشروع، ثم نشر القواعد بعد مراجعتها.
5. إعداد Cloud Functions وSecrets في بيئة الخادم فقط.

## توافق التسجيل
التدفق الحالي في المتجر يعتمد رمز OTP من 6 أرقام. Firebase Auth القياسي للبريد يوفّر التحقق عبر رسالة بريد/رابط وليس نفس تجربة الرمز الرقمي. لذلك لا يُستبدل التدفق بصمت: المرحلة التالية تنفّذ خدمة OTP خادمية محدودة العمر، مع تحديد المعدل ومنع إعادة الاستخدام، أو اعتماد رابط التحقق بعد موافقة المنتج.

## الوظائف الست المطلوب نقلها
1. `apex-wallet-checkout`
2. `apex-create-order`
3. `apex-admin-customers`
4. `apex-ai-guard`
5. `apex-email-campaign`
6. `apex-store-assistant`

يجب نقل منطق التحقق والتسعير والمخزون والعمليات المالية إلى الخادم. لا يُسمح للمتصفح بتحديد السعر النهائي أو تعديل الأرصدة أو منح صلاحية المدير.

## سياسة الترحيل
- لا استيراد بيانات تلقائي.
- لا تحويل DNS/Pages أو نشر إنتاج من هذا الفرع.
- لا تعطيل Supabase في النسخة الحية.
- نقل بيانات تجريبي مع counts/checksums، ثم اختبار الحسابات والطلبات والملفات.
- لا تحويل الإنتاج إلا بعد اختبارات قبول وموافقة صريحة.

## ملاحظة أمنية
مفاتيح Web Firebase العامة ليست أسراراً؛ أما Service Account وResend وOpenAI ومفاتيح بوابات الدفع وبيانات Webhook فهي أسرار خادمية لا تُرفع إلى Git ولا تُضمّن في HTML.


## ربط القراءة العامة للمتجر — دفعة أولى

تم ربط واجهة `index.html` بقراءات Firebase عند وجود إعداد `firebase/runtime-config.js` صالح للمشروع `apex-3c12f`:

- المنتجات النشطة من `products` مع تحويل حقول camelCase إلى أسماء العرض القديمة.
- البنرات النشطة من `banners`.
- وسائل الدفع اليدوية العامة المفعّلة للطلبات من `paymentMethods`.
- سعر الصرف من `storeSettings/currency`.

إذا لم يوجد إعداد Firebase، تستمر الواجهة في استخدام Supabase كما كانت؛ لا يحدث قطع للخدمة ولا تغيير في `main`. هذه الدفعة لا تنقل تسجيل الدخول أو الطلبات أو المحفظة أو لوحة الإدارة، ولا تعني أن بيانات Firebase تمت تعبئتها. قبل تفعيلها يلزم تسجيل Web App ووضع الإعداد العام في ملف runtime المحلي، ثم ترحيل البيانات واختبار الاستعلامات.

**حاجز أمان:** لا تمرر مفاتيح بوابات الدفع أو Service Account إلى المتصفح. تبقى عمليات الطلب والدفع والمحفظة عبر Cloud Functions بعد بنائها والتحقق منها.
